# Сайдкар-файлы `.sfk` / `.sfl` (Sound Forge Peak / Playlist)

Анализ на реальных файлах: [`SAMPLES/veg_project/big-buck-bunny_video-60fps-4k.mp4.sfk`](../SAMPLES/veg_project/big-buck-bunny_video-60fps-4k.mp4.sfk) (2 855 872 B) и
[`…mp4.sfl`](../SAMPLES/veg_project/big-buck-bunny_video-60fps-4k.mp4.sfl) (316 B), лежащих рядом с исходником
`big-buck-bunny_video-60fps-4k.mp4` (743 402 442 B). Оба формата — наследие Sound Forge (Sonic Foundry → Magix), который
Vegas Pro использует как общий audio-движок: при первом добавлении медиафайла в проект Vegas тихо создаёт эти сайдкары
рядом с файлом (один раз) и переиспользует их при повторных открытиях — вместо повторного декодирования всей дорожки.

Оба разобраны здесь **побайтово** (см. скрипты анализа ниже) и сверены с уже реализованным в OpenVegas парсером `.sfk`.
Единица времени `.sfl` (10 000 000 тиков/с) совпадает с уже реверснутым таймбейзом `.veg` — константа
`kTicksPerSec` в `src/io/VegReader.cpp:26` (комментарий там же: «VEGAS Pro uses 10 000 000 ticks per second for edit
times»; см. также обзор формата в [`VEG_READER_V0.md`](VEG_READER_V0.md)).

## 1. `.sfk` — Peak file (кэш waveform)

**Статус в OpenVegas: уже реализовано.** `src/io/MediaWaveformCache.{h,cpp}` (`loadSfk()`, `findSfkBeside()`,
`audioChannelCountHint()`) — используется для быстрой отрисовки waveform на таймлайне (`TimelineView.cpp`), в
`TrimmerWindow`, `AudioEventFxDialog`, `MixingConsoleWindow`, `IconFactory` (иконки-превью аудио) без повторного
декодирования исходника. Этот раздел документирует формат и подтверждает точность существующей реализации на реальном
файле — расхождений не найдено (см. §1.3).

### 1.1 Формат (побайтово, little-endian)

| Offset | Тип | Поле | Значение на сэмпле |
|--------|-----|------|---------------------|
| `0x00` | `char[4]` | magic | `"SFPK"` |
| `0x04` | `u32` | версия | `1` |
| `0x08` | `u32` | размер заголовка (offset начала peak-данных) | `64` |
| `0x0C` | `u32` | не разобрано (похоже на дату/чек-сумму: `0x182F5D01`) | — |
| `0x10` | `u32` | не разобрано (`0x10`) | — |
| `0x14` | `u32` | **каналы** | `6` (Big Buck Bunny — 5.1 surround) |
| `0x18` | `u32` | **сэмплов на 1 peak-бин** | `256` |
| `0x1C` | `u32` | **исходных сэмплов (frames) всего** | `30 461 952` |
| `0x20…0x3F` | — | padding до 64 B | нули |
| `0x40+` | `i16[]` | peak-данные: на бин — `channels × (min, max)`, по 2 B каждое | — |

Длительность не хранится явно — частота дискретизации не записана в файле. `MediaWaveformCache::loadSfk()` угадывает
48000 / 44100 / 192000 Гц эвристикой «какая даёт красивую длительность»; на сэмпле верна `48000` (30 461 952 / 48000 =
634,6 с = 10 мин 35 с — совпадает с реальным хронометражем Big Buck Bunny).

Число бинов = `sourceFrames / samplesPerBin` = `118 992`. Размер peak-данных = `bins × channels × 2 × sizeof(i16)` =
`118 992 × 6 × 2 × 2` = `2 855 808` B. `64 + 2 855 808 = 2 855 872` B — **точное совпадение** с реальным размером файла
(дельта 0).

Первые ~секунды сэмпла — тишина (все min/max = 0), что для Big Buck Bunny ожидаемо (сцена открывается без звука).

### 1.2 Как найти `.sfk` рядом с медиа

Существующая логика (`findSfkBeside()`) уже покрывает оба варианта именования Vegas:

- `name.wav` → `name.wav.sfk` **или** `name.sfk`
- `name.mp4` → `name.mp4.sfk` (только этот вариант — Vegas не пишет `name.sfk` для видео-контейнеров)

### 1.3 Итог по `.sfk`

Ничего внедрять не нужно — реализация уже есть и совпадает с форматом байт-в-байт. Единственное реальное расхождение:
поле `@0x0C` (дата/чек-сумма?) и `@0x10` не используются существующим парсером и не разобраны здесь — они не нужны для
waveform-рендеринга, но если понадобится **инвалидация кэша** (пересоздание `.sfk`, если исходник изменился), стоит
разобрать `@0x0C` отдельно (похоже на `time_t`-подобное значение, `0x182F5D01` = 404 238 081 — не валидный Unix-time,
возможно, own tick-based timestamp Vegas).

## 2. `.sfl` — Playlist / маркеры-регионы медиафайла

**Статус в OpenVegas: не используется нигде.** Ни `grep` по `\.sfl`, ни по `SFPL`/`SFPI` в `src/` ничего не находит.
Это готовая к использованию, но пока не тронутая возможность.

### 2.1 Что это

`.sfl` — не про сам проект `.veg`, а про **конкретный медиафайл**: список маркеров/меток (cue points), которые Sound
Forge/Vegas сохраняет **привязанными к файлу**, а не к проекту. Если тот же `big-buck-bunny_video-60fps-4k.mp4`
перетащить в любой другой проект (или открыть в Sound Forge отдельно), Vegas подхватывает эти же метки — они не
теряются между проектами, в отличие от project-level маркеров `.veg` (которые видны только в конкретном `.veg`).

Формат — валидный RIFF-контейнер (form type `SFPL` — Sound Forge PLaylist), внутри — **стандартные WAV-чанки
`cue `/`LIST/adtl/labl`**, которыми Sound Forge просто переиспользовало под свои маркеры (тот же механизм, которым
`.wav`-файлы искони хранят cue points).

### 2.2 Формат (побайтово)

```text
RIFF <size>                          — форма 'SFPL'
  SFPI <34>                          — имя исходного медиафайла (см. ниже)
  cue  <n*24+4>                      — cue points (стандартный WAV 'cue ' чанк)
  LIST <…> 'adtl'
    labl <…>  ×n                     — текст метки на каждый cue point (стандартный WAV 'labl')
```

| Чанк | Поле | Тип | Комментарий |
|------|------|-----|-------------|
| `SFPI` | имя файла | `char[chunkSize]` | **Без** внутреннего префикса длины — тело чанка целиком ASCII/CP1251-имя, длина = `chunkSize` (наивная попытка трактовать первые 4 B тела как ещё один `u32`-префикс длины даёт мусор — это НЕ вложенная строка Pascal-style, RIFF-заголовок чанка уже несёт длину) |
| `cue ` | `dwCuePoints` | `u32` | число точек (на сэмпле: 5) |
| `cue ` | точка ×n | 24 B каждая | `dwName(u32) dwPosition(u32) fccChunk(char[4]) dwChunkStart(u32) dwBlockStart(u32) dwSampleOffset(u32)` — стандартная раскладка WAV cue point |
| `LIST/adtl/labl` | `cuePointID` | `u32` | ссылается на `dwName` из `cue ` |
| `LIST/adtl/labl` | текст | `char[]`, NUL-terminated | кодировка **CP1251** (кириллица — Vegas сохраняет в локальной кодировке ОС, не UTF-8/UTF-16!) |

`dwPosition` **и** `dwSampleOffset` в этом файле совпадают и оказались **не** сэмплами при родной частоте дискретизации
аудио (как предполагает стандарт WAV), а **тиками по 10 000 000/с** — тем же таймбейзом, что и `.veg`
(`kTicksPerSec` в `VegReader.cpp`). Проверено делением на кандидатов частот: только `/10 000 000` даёт правдоподобные
позиции (доли секунды — единицы минут) в пределах реальной длительности файла (10 мин 35 с по `.sfk`); деление на
44100/48000 давало бы неправдоподобные ×200-кратно раздутые времена.

### 2.3 Реальные данные на сэмпле

5 маркеров, все на дорожке `data` (chunkStart/blockStart = 0):

| # (`dwName`) | Позиция (тики) | Время | Текст метки (CP1251) |
|---|---|---|---|
| 1 | 2 053 600 | 0:00.205 | `аудио 1` |
| 2 | 4 248 000 | 0:00.425 | `2 аудио` |
| 3 | 152 995 556 | 0:15.300 | `вторая метка` |
| 4 | 212 000 000 | 0:21.200 | `метка первая` |
| 5 | 1 913 822 837 | 3:11.382 | `метка первая` (тот же текст, что и у #4 — вероятно, тестовые данные) |

Все пять укладываются в реальный хронометраж файла (10:35 по `.sfk`) — согласованность подтверждает и разбор `.sfl`,
и разбор `.sfk`, и (независимо) уже задокументированный тик-конвеншн `.veg`.

### 2.4 Предложение по применению в OpenVegas

В проекте уже есть ровно подходящее место: `MediaItem::markers` (`QVector<TimelineMarker>`,
`src/model/ProjectModel.h:748`) — «Event Media Markers», отображаемые в `TrimmerWindow` (не путать с ruler-маркерами
проекта). Уже есть прецедент автозаполнения этого поля из эвристики: `detectBeatsIntoMediaItem()` +
`seedSampleAudioBeatMarkersIfNeeded()` (`ProjectModel.cpp:1264`) — beat-detection для одного конкретного сэмпл-файла.
`.sfl` — тот же карман, но с **точными**, а не эвристическими данными, и для **любого** медиафайла, у которого есть
сайдкар.

Конкретный план:

1. **Новый ридер** `src/io/MediaMarkerSidecar.{h,cpp}` (или расширить `MediaWaveformCache`, раз он уже владеет
   `findSfkBeside()`-подобной логикой поиска сайдкаров рядом с медиа) — функция вида
   `QVector<TimelineMarker> loadSflMarkers(const QString &mediaPath)`:
   - найти `mediaPath + ".sfl"` (аналогично `findSfkBeside`, тот же паттерн именования);
   - проверить `RIFF`/`SFPL`;
   - пройти `cue `+`LIST/adtl/labl`, сматчить `labl.cuePointID` → `cue.dwName`;
   - `timeSec = dwPosition / 10 000 000.0` (переиспользовать константу тиков — либо вынести `kTicksPerSec` из
     `VegReader.cpp` в общий заголовок, либо продублировать с комментарием-ссылкой);
   - декодировать текст `labl` как **CP1251** (`QTextCodec`/`QStringDecoder` для `"Windows-1251"`), не UTF-8.
2. **Точка подключения**: `ProjectModel::ensureMediaItem()` (`ProjectModel.cpp:1173`) — единая точка создания
   `MediaItem`. Сразу после `item.missing = …`, если `item.markers.isEmpty()` и рядом есть `.sfl` — заполнить.
   Это разом покрывает и импорт медиа через UI, и открытие `.veg` (оба пути стекаются в `ensureMediaItem`).
3. **UI**: ничего рисовать заново не нужно — `TrimmerWindow` и `showEventMediaMarkers()`
   (`ProjectModel.h:901`) уже умеют показывать `MediaItem::markers`; они просто начнут не быть пустыми для файлов с
   `.sfl`.
4. **Реэкспорт** (опционально, отдельная задача): если пользователь добавляет/двигает Event Media Marker в
   OpenVegas, можно сохранять это обратно в `.sfl` рядом с файлом — тогда поведение будет соответствовать Vegas
   Pro и в обратную сторону (метки переживают проект). Не обязательно для v1 — только чтение уже даёт пользу.

### 2.5 Ограничения / что проверить перед внедрением

- Кодировка `labl` в этом файле — CP1251 (кириллица), но у не-русской копии Vegas может оказаться другая codepage
  (или UTF-16 в новых версиях) — при реализации стоит сначала попробовать UTF-8/ASCII-safe decode, откатываясь на
  CP1251 только если результат содержит непечатаемые символы (похожий паттерн уже есть в `VegReader.cpp` —
  `isPrintableUtf16Char`).
- `dwChunkStart`/`dwBlockStart` в сэмпле всегда 0, `fccChunk` всегда `"data"` — упрощение (не multi-chunk WAV);
  ридер может не поддерживать multi-`data`-chunk файлы, это не встречается в реальных Vegas-экспортах.
- Один `.sfl` = маркеры одного медиафайла (не регион/subclip с длиной — судя по составу `cue `, это point-маркеры, не
  диапазоны; полей длины региона в этом чанке нет).

## 3. Скрипты анализа (для воспроизводимости)

Побайтовый разбор обоих файлов делался разовыми Python-скриптами (не входят в репозиторий) — RIFF-обходчик +
раздельная интерпретация `.sfk`-заголовка. При необходимости то же самое воспроизводится в incremental C++ так же,
как уже сделано в `MediaWaveformCache::loadSfk()` — она и есть эталонная, проверенная реализация для `.sfk`;
для `.sfl` реализации пока нет (см. §2.4).
