# Аппаратные ускорители (VLD-декод, NVENC / QSV / AMF)

Состояние на 2026-08-11. Всё ускорение идёт через FFmpeg — своего слоя работы с
D3D11/CUDA/VA-API у нас нет и не планируется.

## Что такое VLD и где он у нас

VLD (Variable Length Decoding) — entrypoint **полного** аппаратного декода в
DXVA2 / D3D11VA / VA-API, в отличие от частичных режимов (IDCT, MoComp), где GPU
берёт на себя лишь часть конвейера. Практически любой современный аппаратный
декод — это VLD.

У нас он включается в `hwAccelPrefix()` ([FFmpegStreamDecoder.cpp](../src/io/FFmpegStreamDecoder.cpp))
как `-hwaccel <метод>` перед `-i`. Метод берётся из `hwDecodeMethod()`.

Список методов не хардкодится — он читается из `ffmpeg -hwaccels`
(`availableHwDecodeMethods()`). На машине разработки (ffmpeg 8.1 Gyan full):

```
cuda  vaapi  dxva2  qsv  d3d11va  opencl  vulkan  d3d12va  amf
```

`auto` отдаёт выбор самому ffmpeg — на Windows он обычно приходит к `d3d11va`
или `dxva2`. Явно заданный метод, которого нет в этом списке, **молча
деградирует в `auto`**: иначе устаревшая настройка ломала бы вообще любой декод.

## Главный урок: «перечислен» ≠ «работает»

Это центральная вещь во всей теме, и на ней уже был баг.

`ffmpeg -encoders` печатает **статический список того, что скомпилировано в
бинарник**. Он не зависит от машины. В полных сборках (Gyan, BtbN) там всегда
есть и `h264_nvenc`, и `h264_qsv`, и `h264_amf` — на любом компьютере.

Проверено на машине разработки (Ryzen 7 7700 + RTX 4070 + Radeon iGPU, Intel-части нет):

```
$ ffmpeg -encoders | grep h264_qsv
 V..... h264_qsv    H.264 / AVC ... (Intel Quick Sync Video acceleration)

$ ffmpeg -f lavfi -i testsrc -frames:v 3 -c:v h264_qsv -f null -
[h264_qsv] Error creating a MFX session: -9.
[h264_qsv] The current mfx implementation is not supported
exit=171
```

То есть кодек **перечислен и не работает одновременно**.

Старый `videoEncodeCodecArgs()` выбирал кодек по одному лишь наличию в списке, с
жёстким порядком NVENC → QSV → AMF. Значит на любой машине он выбирал
`h264_nvenc` — и на компьютере без NVIDIA каждый рендер падал бы на инициализации
энкодера. У нас это было замаскировано тем, что на dev-машине NVENC есть и правда
работает.

### Как чинится

`encoderUsable()` вместо `encoderAvailable()`. Он выполняет **пробный энкод трёх
кадров** `testsrc` в `-f null -` и смотрит код возврата:

```
ffmpeg -hide_banner -loglevel error -f lavfi -i testsrc=size=256x144:rate=25 \
       -frames:v 3 -c:v <кодек> -f null -
```

Замеры стоимости на dev-машине:

| Кодек | Код возврата | Время |
|-------|--------------|-------|
| `h264_qsv` | 171 (нет Intel) | 81 мс |
| `h264_nvenc` | 0 | 205 мс |
| `h264_amf` | 0 | 100 мс |
| `libx264` | 0 | 62 мс |

Вердикт кэшируется в памяти и в `QSettings` под `media/encoderProbe/<кодек>`,
поэтому платим один раз. Кэш привязан к `media/encoderProbeFingerprint` —
строке «путь|размер|mtime» бинарника ffmpeg: подменили ffmpeg — вердикты
сбрасываются автоматически.

Явный выбор кодека пользователем **тоже** проходит проверку. Если выбрать QSV на
AMD-машине, будет мягкий откат на libx264, а не сломанный рендер.

## Настройки

| Ключ `QSettings` | Переменная окружения | Значения | По умолчанию |
|------------------|----------------------|----------|--------------|
| `media/hwAccel` | `OPENVGAS_HWACCEL` | `1`/`0`, `on`/`off`, `true`/`false` | `true` |
| `media/hwDecoder` | `OPENVGAS_HWDECODER` | `auto` или имя из `ffmpeg -hwaccels` | `auto` |
| `media/hwEncoder` | `OPENVGAS_HWENCODER` | `auto`, `nvenc`, `qsv`, `amf`, `cpu` | `auto` |

Переменная окружения имеет приоритет над `QSettings` — удобно для CI и для
разовой проверки без правки настроек.

UI: **Preferences → Video**. Там же кнопка **Detect…**, которая сбрасывает кэш и
перезапускает пробные энкоды (нужна после смены GPU или драйвера), и строка
статуса вида:

> Works here: h264_nvenc, h264_amf. Not usable on this machine: h264_qsv.

Показывать разницу «есть в сборке / не заводится здесь» — сознательное решение:
именно это расхождение и было источником бага.

## Известная дыра: линкованный libav не использует hwaccel

`decodeSequence()` при сборке с `OPENVGAS_FFMPEG` **сначала** пробует
`decodeSequenceLibav()`, и только если та вернула 0 — уходит на CLI-путь с
`-hwaccel`.

А `decodeSequenceLibav()` делает обычный `avcodec_open2()` **без**
`av_hwdevice_ctx_create()` и без коллбэка `get_format`. То есть это чистый
софтверный декод. **Сборка с линкованным FFmpeg молча отключает аппаратный
декод.**

Сейчас это не проявляется: `OPENVGAS_FFMPEG` включается только если pkg-config
находит `libavcodec` и т.д., а на dev-машине dev-библиотек FFmpeg нет, поэтому
код не собирается и не выполняется. По этой же причине **правка не сделана** —
писать заметный кусок работы с `AVBufferRef`/`av_hwframe_transfer_data` в путь,
который здесь физически нечем скомпилировать, значит закоммитить непроверенный
код.

Что нужно для закрытия:

1. Поставить dev-пакеты FFmpeg, чтобы `OPENVGAS_FFMPEG` включился.
2. В `decodeSequenceLibav()`: `av_hwdevice_ctx_create()` (d3d11va на Windows,
   vaapi на Linux, videotoolbox на macOS), `get_format`, возвращающий hw-формат,
   и `av_hwframe_transfer_data()` для переноса кадра в системную память.
3. Мягкий откат на софт при любой ошибке инициализации — как сделано для энкода.

## Про ожидания от производительности

Стоит держать в голове честную картину, иначе ускорители выглядят волшебной
кнопкой, которой они не являются.

**Где выигрыш реальный:**

- **Экспорт (Render As).** Кодирование целиком уезжает на GPU. Здесь профит
  измеряется разами.
- **Скраб и превью тяжёлых исходников** — 4K, HEVC, 10 бит. Софтверный декод
  таких потоков действительно упирается в CPU.

**Где выигрыша почти нет:**

- **Обычный 1080p H.264.** Софтверный декод и так не узкое место.
- **Превью вообще.** `VideoCompositor` работает с `QImage` в системной памяти.
  Аппаратный декод отдаёт кадр в память GPU, и чтобы дойти до `QImage`, нужен
  readback через шину плюс конверсия NV12 → RGB. Это съедает заметную часть
  выигрыша, а иногда и весь.

Настоящее ускорение превью даёт не смена декодера, а перенос композитинга на
GPU. Это переписывание `VideoCompositor`, а не опция в настройках, и в текущие
планы не входит.

## Регрессионные тесты

`tests/test_ffmpeg_stream_decoder.cpp`, тег `[encoder-probe]`:

- «Only an encoder that survives a trial run counts as usable» — «работает»
  обязано влечь «перечислен», и никогда наоборот.
- «videoEncodeCodecArgs only names an encoder that actually runs here» — что бы
  ни выбрала логика, этот кодек проходит пробный энкод.
- «An explicit hardware encoder that cannot run falls back to software» — явный
  выбор не обходит проверку; неизвестное имя и `cpu` дают libx264.
- «hwDecodeMethod rejects a method this ffmpeg does not offer» — устаревшая
  настройка деградирует в `auto`, а не ломает декод.
