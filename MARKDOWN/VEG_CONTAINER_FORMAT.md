# Контейнер `.veg`: riff64

Разобрано по `vegas220.exe` и `sharedk.dll` через Ghidra (headless-анализ, 12.1.2), плюс
сверка с реальными проектами из `SAMPLES/veg_project/`.

До этого `.veg` читался **сканированием файла** на известные GUID с чтением по
фиксированным смещениям от находки. Это работало, но не могло ответить на вопрос «какому
событию принадлежит запись» — владелец угадывался по порядку байт. Оказалось, что формат
полностью самоописывающийся, и на этот вопрос он отвечает сам.

## Это RIFF, только с GUID вместо FOURCC

Заголовок чанка: **16 байт идентификатора + int64 размер**, и размер **включает сам
заголовок**. Два идентификатора выдают происхождение — их первые четыре байта это ASCII:

| идентификатор | первые байты | что это |
|---|---|---|
| `{66666972-912E-11CF-A5D6-28DB04C10000}` | `riff` | корневой чанк файла |
| `{7473696C-912F-11CF-A5D6-28DB04C10000}` | `list` | контейнер |

`riff` и `list` несут **тип формы** — ещё 16 байт сразу после размера, ровно как в RIFF
после `RIFF`/`LIST` идёт `WAVE`/`INFO`. Значит, заголовок списка 40 байт, а не 24.

### Подтверждение из кода самой VEGAS

Не предположение — так написан хостовый ридер. `sharedk.dll` экспортирует 34 функции
`riff64_*`, и две из них решают вопрос о семантике размера:

```c
riff64_ReadChunkHeader(HANDLE h, LPVOID idOut, longlong *sizeOut)
{
    ReadFile(h, idOut,  0x10, ...);   // 16 байт идентификатора
    ReadFile(h, sizeOut, 8,   ...);   // int64 размер
    *sizeOut = *sizeOut - 0x18;       // ← минус 24: размер считал и заголовок
    if (*sizeOut < 0) *sizeOut = 0;
}

riff64_ReadListHeader(HANDLE h, LPVOID formTypeOut, longlong *sizeOut)
{
    ReadFile(h, id, 0x10, ...);
    ReadFile(h, sizeOut, 8, ...);
    *sizeOut -= 0x18;
    if (memcmp(&LIST_GUID, id, 0x10) != 0) return 0x8004E081;  // «это не список»
    *sizeOut -= 0x28;                 // ← минус 40: у списка ещё и тип формы
    ReadFile(h, formTypeOut, 0x10, ...);
}
```

То есть на диске размер включает заголовок, а API отдаёт наружу размер полезной нагрузки.
Коды ошибок: `0x8004E008` — короткое чтение, `0x8004E081` — чанк не является списком.

Остальной API (`riff64_FindListChunk`, `riff64_SeekListEntry`, `riff64_GetNumListEntries`,
`riff64_PrepareChunk` / `riff64_CompleteChunk` / `riff64_UpdateRIFFSize` для записи)
подтверждает ту же модель: список — это последовательность записей, по которым ходят
индексом.

Заметка на будущее: `riff64_getGUIDLabel` и `riff64_getGUIDLabelProperly` в релизной
сборке — **заглушки, возвращающие 0**. Человекочитаемых имён чанков в поставке нет,
называть их приходится по тому, что с ними делает код.

Все 38 различных идентификаторов из этого файла лежат в `vegas220.exe` **одной сплошной
таблицей** в `.rdata` (файловое смещение 0xd2d560…, RVA 0x140d2e160…) — это собственный
реестр чанков хоста. Перекрёстные ссылки показывают, что `FUN_140787e30` обращается почти
ко всем: это диспетчер чтения проекта.

## Слот плагина `{FC2B3BCF-…}`

Здесь лежит переход и вообще любой FX события:

```
+0x00  int32   длина фиксированного заголовка (0x90 в виденных сборках)
+0x04  …       фиксированные поля; среди них по +0x70 int32:
                 1 = запись на fade-in (кроссфейд хранится так же), 0 = fade-out
+hdr   int32   длина записи плагина (0x38)
+hdr+4 GUID    CLSID плагина
       +48     int32 длина имени пресета в БАЙТАХ, включая нулевой терминатор UTF-16
       +52     само имя пресета (UTF-16)
       далее   параметры плагина
```

**Смещение CLSID задаётся полем длины, а не константой.** Читать его по фиксированному
`0x94` получается только потому, что заголовок здесь именно такой длины. Слот длиной ровно
в заголовок (144 байта) — **пустой**: это событие с фейдом, но без перехода. В разобранном
проекте 16 слотов, из них заполнено 12 — ровно столько переходов в нём и есть, остальные
четыре фейда пустые. Тест на это есть; первая версия теста утверждала константу `0x94` и
провалилась на четырёх пустых слотах — так эта деталь и нашлась.

## Маркер `{ABF76256-…}`

```
+0x00  int64  длина собственного заголовка (0x28 = 40)
+0x08  int64  позиция в единицах 100 нс
+0x10  int64  длительность
+0x18  int32  номер
+0x20  int64  длина метки в байтах, с терминатором
+0x28  метка UTF-16
```

## Что это дало коду

`src/io/VegRiff.{h,cpp}` — обход контейнера. `VegReader` больше не угадывает владельца
перехода: запись вложена в своё событие, и `vegRiffEnclosing()` его находит. Прежняя
эвристика — «последнее видеособытие, чей заголовок начинается раньше записи» — оставлена
запасным путём для файла, который не открывается как контейнер: она совпадает с истиной,
пока файл записан в обычном порядке, но отличить запись **внутри** события от записи,
которая просто идёт **следом**, она не может.

Сверка: смещения, снятые ранее вручную по дампу (`GUID+48` — длина имени, `GUID+52` — имя,
`GUID−36` — признак fade-in), сошлись с чанковой структурой байт в байт.

## Запись контейнера и что она доказала

[`src/io/VegRiffWriter.*`](../src/io/VegRiffWriter.h) сериализует дерево чанков обратно в
байты. Размеры считаются из дерева: размер, написанный рукой, — это размер, который может
разойтись с тем, что за ним лежит.

Ценность здесь не в самой записи, а в проверке, которую она делает возможной: **все 24 из 24
сэмплов читаются в дерево и пишутся обратно побайтно**. Это единственный доступный способ
убедиться, что модель верна везде, куда достаёт файл, а не только в местах, которые смотрели
глазами:

- где кончается заголовок (24 байта у чанка, 40 у списка);
- что размер считает сам себя — то самое `-= 0x18` из `riff64_ReadChunkHeader`;
- у каких идентификаторов есть тип формы;
- что между чанками ничего не выравнивается (в классическом RIFF — выравнивается).

Ошибка на байт в любом из этих мест, и файл вернулся бы другим. Байты внутри списка, которые
не разобрались как чанки, сохраняются как есть — чтобы неудачный round-trip обвинял модель, а
не файл.

Чего это **не** доказывает: что файл, собранный нами с нуля, откроется в самой VEGAS. Для
этого нужно знать, какие чанки обязательны и что лежит внутри каждого, — а контейнер отдаёт
границы, но не содержимое.

## Чего это ещё не решает

Разбор параметров плагинов после имени пресета остаётся индивидуальным для каждого
плагина — контейнер отдаёт границы блока, но не его содержимое. Для Sound Forge это
по-прежнему открытый пункт (см. [ISSUES_AND_PLANS.md](ISSUES_AND_PLANS.md)).
