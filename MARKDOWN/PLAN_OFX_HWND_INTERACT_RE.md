# Нативные формы OFX-плагинов (`OfxHWndInteractSuite`) — план реверса

Как дать плагинам VEGAS рисовать **свой** интерфейс вместо наших ползунков.

Родительский разбор: [`PLAN_OFX_VIDEO_PLUGINS.md`](PLAN_OFX_VIDEO_PLUGINS.md).
Журнал: [`ISSUES_AND_PLANS.md`](ISSUES_AND_PLANS.md).

**Статус:** этап 0 выполнен (2026-08-12) и **изменил постановку задачи** — см. «Результаты
этапа 0». **Этап 2 закрыт** (2026-08-21): раскладка `OfxHWndInteractSuite` восстановлена
декомпиляцией, перепроверена независимо и реализована в хосте — разбор в
[`RE_OFX_HWND_INTERACT_REPORT.md`](RE_OFX_HWND_INTERACT_REPORT.md), раздел 4а.
Остаются этап 1 (провести `CreateWindow` вживую) и этап 3 (встроить окно в Qt);
этап 4 (overlay-ветка) — отдельно, там разбора ещё не делали.

---

## Цель

Chroma Blur в VEGAS показывает собственную панель (заголовок «VEGAS Chroma Blur», кнопки
`About` / `?`, свои поля со стрелками кейфреймов), а у нас — сгенерированные ползунки.
Цель — хостить настоящий UI плагина.

### Non-goals

- **Glint («Мерцание»).** Его белая форма к OFX отношения не имеет: Glint вообще не
  экспортируется ни одним бандлом (78 эффектов в `Vfx1.ofx` против 102 в манифесте), это
  внутренний плагин VEGAS, и окно рисует сам VEGAS. Никакая работа по этому плану его не вернёт.
- Overlay-interact поверх видео (`OfxHWndOverlayInteractSuite`) — отдельная, более поздняя тема.
- Linux / macOS. HWND — понятие Windows; вне Windows бандлы VEGAS и так не грузятся
  (ABI-гейт), а параметрический UI остаётся везде.

---

## Что известно (по фактам, не по догадкам)

Строки в `Vfx1.ofx` (полные литералы в секции данных):

| Категория | Имена |
|---|---|
| Suite | `OfxHWndInteractSuite`, `OfxHWndOverlayInteractSuite` |
| Свойство плагина | `OfxImageEffectPluginPropHWndInteractV1`, `…HWndOverlayInteractV1` |
| Свойства interact | `OfxHWndInteractPropParent`, `…PropLocation`, `…PropMinSize`, `…PropPrefferedSize` |
| Действия | `OfxHWndInteractActionCreateWindow`, `…MoveWindow`, `…ShowWindow`, `…DisposeWindow` |

Опечатка `Preffered` — та же, что в заголовке Sony/MAGIX SDK: строки взяты оттуда дословно,
значит и остальные имена можно считать точными.

**Главное, что показала трасса** (`OPENVEGAS_OFX_TRACE`, Chroma Blur):

```text
getInt host[OfxImageEffectPropSupportsOverlays][0] = 0 -> 0
getInt host[OfxParamHostPropSupportsCustomInteract][0] = 0 -> 0
fetchSuite("OfxHWndInteractSuite", v1) -> NULL
fetchSuite("OfxHWndOverlayInteractSuite", v1) -> NULL
```

и при этом за весь `Describe` / `DescribeInContext` плагин **ни разу не выставляет**
`OfxImageEffectPluginPropHWndInteractV1`.

Вывод: плагин спрашивает у хоста разрешение (`SupportsOverlays`, `SupportsCustomInteract`),
получает «нет» и свой interact просто не регистрирует. То есть **мы ещё не видели, как он себя
ведёт, когда хост говорит «да»** — и это меняет порядок работ: сначала дешёвый эксперимент,
и только потом дорогой реверс.

---

## Почему раскладка suite — трудная часть

`fetchSuite` обязан вернуть указатель на структуру из функциональных указателей. Порядок и
сигнатуры полей не опубликованы. Заглушка с угаданной раскладкой = вызов функции неверной
арности по неверному смещению = падение приложения внутри чужого кода. Поэтому сейчас
честно возвращается `NULL`.

Но обратите внимание на асимметрию: **действия идут host → plugin** (это `mainEntry`, чью
сигнатуру мы знаем), а suite нужен для обратного направления, plugin → host. Если плагин
на этапе создания окна к хосту не обращается, значительную часть пути можно пройти вообще
без раскладки suite.

## Этапы

### Этап 0 — сказать «да» и посмотреть (дёшево, без реверса)

1. В `initHostProps()` выставить `kOfxImageEffectPropSupportsOverlays = 1` и
   `kOfxParamHostPropSupportsCustomInteract = 1`.
2. Дать `kOfxPropHostOSHandle` реальный HWND главного окна (сейчас `nullptr`).
3. Прогнать трассу заново.

**Что выяснится:** появится ли `setPointer …HWndInteractV1` в трассе Describe, и какие suite
плагин затребует после этого. Возможен и отрицательный исход — плагин, увидев «да», может
потребовать suite прямо на `Load` и отвалиться с `kOfxStatErrMissingHostFeature`. Это тоже
результат: тогда порядок этапов 1 и 2 меняется местами.

**Риск:** флаги влияют на весь рендер-путь. Прятать за отдельным флагом сборки/переменной
окружения (`OPENVEGAS_OFX_INTERACT=1`), пока не устоится.

**DoD:** в трассе видно, публикует ли плагин указатель на interact.

### Результаты этапа 0 (2026-08-12)

Реализовано: `OPENVEGAS_OFX_INTERACT=1` включает оба флага поддержки и отдаёт на оба
HWnd-suite **пробную таблицу** из 32 логирующих заглушек (`interactProbe<N>` в
[`OfxHost.cpp`](../src/plugins/OfxHost.cpp)). По умолчанию выключено.

Что показала трасса:

1. Плагины принимают suite (`fetchSuite("OfxHWndInteractSuite", v1) -> ok`), `Load`,
   `Describe`, `DescribeInContext` и `Render` по-прежнему `status 0` — включение флагов
   ничего не ломает.
2. **Ни одного вызова PROBE.** Значит suite на этапе описания не используется вовсе, и
   раскладка нужна только позже, при создании окна — как и предполагал этап 2.
3. **Chroma Blur своего UI не имеет.** Даже с флагами «да» он объявляет только label,
   grouping, два клипа, два `Double`-параметра и uplift GUID. Никакого interact.

Сканирование **всех** бандлов (Describe по каждому эффекту) нашло ровно два объявления:

| Эффект | Свойство |
|---|---|
| `com.vegascreativesoftware:colorcurves` | `OfxImageEffectPluginPropHWndInteractV1` |
| `com.vegascreativesoftware:titlesandtext` | `OfxImageEffectPluginPropHWndOverlayInteractV1` |

**Вывод, меняющий постановку.** Белая панель Chroma Blur в VEGAS — это не форма плагина, а
**собственная панель параметров VEGAS**, построенная из тех же двух `Double`, что видим мы;
отличается только оформление. Строки `OfxHWnd*` лежат в каждом бинарнике потому, что они из
общего Sony/MAGIX SDK, а не потому, что эффект ими пользуется.

Отсюда:

- Задача «дать плагинам рисовать свой UI» касается **ровно одного** эффекта — Color Curves
  (и Titles & Text по overlay-ветке). Для остальных 76 нативной формы не существует.
- Чтобы панели выглядели как в VEGAS, реверс suite не нужен — нужна **стилизация нашей
  панели параметров** (заголовок с именем плагина, `About` / `?`, поля со стрелками
  кейфреймов). Это несравнимо дешевле и покрывает весь каталог.
- Реверс `OfxHWndInteractSuite` остаётся оправданным только ради Color Curves, где нативный
  редактор кривых действительно даёт то, чего наш параметрический UI не даст.

Приоритет этапов 1–2 после этого падает: сначала стилизация панели, затем декодер параметров
из `.veg`, и только потом Color Curves.

### Этап 1 — вызвать interact без suite

Если указатель публикуется:

1. Читать его из дескриптора (`PropValue::Pointer` уже поддерживается) как
   `OfxPluginEntryPoint *` — так же, как это делает стандартный
   `kOfxImageEffectPluginPropOverlayInteractV1`.
2. Создать QWidget-контейнер, взять его `winId()` как родительский HWND.
3. Послать `OfxHWndInteractActionCreateWindow` с inArgs:
   `OfxHWndInteractPropParent` (наш HWND, pointer), `OfxHWndInteractPropLocation`
   (int×2 или int×4 — уточнить по трассе чтений), затем прочитать из outArgs
   `OfxHWndInteractPropMinSize` / `…PropPrefferedSize`.
4. Дальше `…ShowWindow`, на resize — `…MoveWindow`, на закрытие — `…DisposeWindow`.

Порядок и типы аргументов **выясняются трассой**: наш `propGet*` логирует каждое обращение
с именем свойства, так что плагин сам покажет, что он ждёт и в каком типе.

**DoD:** окно плагина появилось внутри нашего диалога хотя бы статически.

### Этап 2 — восстановить раскладку suite **пробным suite**, а не дизассемблером

Ключевая идея: раскладку не надо угадывать — её можно **измерить**.

1. Отдать на `fetchSuite("OfxHWndInteractSuite", 1)` массив из N (взять с запасом, 32)
   различных функций-заглушек `probe0…probe31`, каждая из которых логирует
   «вызван слот i», дамп первых 4 аргументов как `void*`/`int` и возвращает `kOfxStatFailed`.
2. Запустить сценарий этапа 1. Плагин сам вызовет нужные слоты — **номер слота в логе и есть
   смещение в структуре**.
3. По аргументам и по тому, что плагин делает дальше, восстановить сигнатуры по одной.
   Сверять с именами свойств: набор `Parent / Location / MinSize / PrefferedSize` маленький,
   значит и функций в suite немного.

**Почему это безопасно на x64:** соглашение вызова единое и caller-cleanup, поэтому лишние
или недостающие аргументы сами по себе стек не рушат. Опасно другое — если заглушка вернёт
«успех», не заполнив out-параметр, плагин прочитает мусор. Поэтому первая итерация возвращает
**ошибку** и ничего не пишет: плагин должен аккуратно отступить, а мы получим лог. Заполнять
out-параметры — только на второй итерации, по одному, зная сигнатуру.

**Страховка:** прогонять под отдельным процессом-хелпером или хотя бы с
`OPENVEGAS_OFX_THREADS=1` и включённой трассой; падение внутри плагина ожидаемо и не должно
уносить проект пользователя.

**DoD:** документированная раскладка `OfxHWndInteractSuiteV1` — имя, индекс, сигнатура на
каждое поле — в этом файле.

### Результаты статического реверса (2026-08-21, Ghidra + MCP)

Вместо пробного suite раскладка снята статически из `Vfx1.ofx` (Ghidra 12.1.2 + GhidraMCP;
настройка стека и полные выкладки — [`RE_OFX_HWND_INTERACT_REPORT.md`](RE_OFX_HWND_INTERACT_REPORT.md),
дампы — `build/re-ghidra/extract/`). Ключевое:

1. **Диспетчер найден:** `FUN_180487cc0` = `hwndInteractMainEntry`, внутри `FUN_180487a10`
   разбирает действия по `kOfxPropActionType`. Аргументы действий подтверждены по коду:
   `CreateWindow` читает `OfxHWndInteractPropParent` (pointer) и пишет в outArgs
   `MinSize` int×2 + `PrefferedSize` int×2; `MoveWindow` читает `Location` int×4;
   `ShowWindow`/`DisposeWindow` без аргументов.
2. **Suite нужен плагину ровно в двух слотах:** +0x00
   `getPropertySet(interactHandle, OfxPropertySetHandle*)` и +0x08 — функция одного
   аргумента-handle, вызывается legacy-диалоговым кодом после `InvalidateRect`
   (вероятно redraw/уведомление хоста; семантика не подтверждена). Остальные слоты
   плагин не вызывает вовсе.
3. **Vtable C++-объекта interact** (сторона плагина): +0x00 destroy, +0x08 createWindow(parent)
   (реализация `FUN_1802bd7e0` — Win32-диалог из ресурса шаблона), +0x10 moveWindow(int[4]),
   +0x18 disposeWindow, +0x20 showWindow. RTTI: `colorcurvesInteract`,
   `OFX::HWNDInteractMainEntry<colorcurvesInteractDescriptor>` и др.
4. Interact-handle property set: хост пишет `OfxPropEffectInstance`, плагин —
   `OfxPropInstanceData` (его C++ объект).

Следствие для этапа 2: пробный suite больше не нужен как основной инструмент — достаточно
реализовать слоты +0x00 и +0x08 (остальные — заглушки с `kOfxStatFailed`) и идти сразу в
этап 1: `CreateWindow(Parent)` → чтение MinSize/PrefferedSize → `ShowWindow`.
Осталось подтвердить семантику слота +0x08 уже в рантайме.

### Этап 3 — встроить окно в Qt по-настоящему

1. `QWidget::createWindowContainer` / `QWindow::fromWinId` для окна, которое создал плагин.
2. Прокинуть resize → `…MoveWindow`, показ/скрытие → `…ShowWindow`, закрытие диалога →
   `…DisposeWindow` (обязательно до разрушения родителя).
3. Уважать `MinSize` / `PrefferedSize` при первичном размере панели.
4. Синхронизация значений: параметры, изменённые в родной форме, должны доезжать до
   `FxSlot.state`. Механизм — тот же `paramSetValue`, который у нас уже реализован; проверить,
   что плагин им пользуется, и подхватывать изменения.

**DoD:** панель Chroma Blur живёт в диалоге Video Event FX, значения синхронны с проектом.

### Этап 4 — overlay поверх превью (опционально)

`OfxHWndOverlayInteractSuite` + действия `Draw` / `MouseDown|Move|Up` / `KeyDown|Up|Char` /
`GainFocus|LoseFocus` и свойства `HDC`, `MouseLoc`, `KeyCode`, `Rect`. Та же техника пробного
suite. Нужен только для эффектов с экранными манипуляторами; к панели параметров отношения
не имеет.

## Условия остановки

Работа прекращается с write-up (а не тянется бесконечно), если:

- на этапе 0 плагин требует suite уже на `Load` **и** пробный suite этапа 2 не даёт
  воспроизводимой картины вызовов за разумное время;
- родная форма поднимается, но не синхронизирует значения с хостом — тогда она хуже наших
  ползунков, и её включать нельзя;
- выясняется, что форма требует ещё и `OfxPropHostIUnknown` (COM-интерфейс хоста VEGAS) —
  это отдельный и гораздо больший объём, который в этом плане не покрыт.

Во всех случаях параметрический UI остаётся рабочим fallback'ом; нативная форма — надстройка,
а не замена.

## Порядок ценности

Замечание для приоритизации: нативные формы — **косметика по сравнению с тем, что эффекты из
`.veg` вообще не видны**. Сначала стоит закрыть декодер OFX-блоба параметров (см. родительский
план), иначе получится красивая родная панель у эффекта, который ничего не рисует.
